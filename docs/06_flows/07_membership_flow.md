# Membership Flow

## Membership Objective

DALC membership should be a real recurring product that changes service quality, priority, and economics. It should not launch as decorative status.

## Membership Value Proposition

DALC membership should promise three concrete advantages:

1. faster response and priority handling
2. continuity across repeat requests
3. better economics on premium recurring usage

If DALC cannot reliably deliver those three outcomes, membership should not be sold yet.

## Tier Structure

| Tier | Who it is for | Strategic role |
| --- | --- | --- |
| Core | Users with recurring but moderate premium demand | Entry recurring layer |
| Premium | High-value users who want faster response and deeper support | Main retention tier |
| Elite | Very high-touch clients with urgent and custom demand | White-glove economics layer |

## Entitlements

| Tier | Entitlements |
| --- | --- |
| Core | Faster response, request history continuity, selected booking benefits |
| Premium | Priority queueing, concierge planning support, preferred execution economics, recurring request convenience |
| Elite | Highest priority, dedicated handling patterns, premium recovery, best execution responsiveness |

## Billing Logic

Membership should be monthly or annual and charged through a clean recurring billing system tied to priority handling logic.

Billing rules:

1. no hidden bespoke membership pricing at launch
2. no fake discounts without operational value
3. no membership promises disconnected from queue priority and execution support

## Priority Handling Logic

| Situation | Membership effect |
| --- | --- |
| Similar request volume between users | Member request gets higher queue priority |
| Urgent custom request | Premium and elite members receive faster operator response |
| Service failure | Member recovery path should trigger faster |

## Upsell Timing

Membership should be sold at moments of proven value, not at first contact.

Best timing:

1. after a successful high-touch request
2. after repeated premium usage
3. during a quote flow where priority matters
4. after relocation or setup completion when ongoing support is the logical next step

## Retention Logic

Retention depends on visible ongoing value.

That means DALC should maintain:

1. request continuity
2. preference memory
3. faster response times
4. clear member-only handling advantages

## Cancellation Logic

Cancellation should be straightforward and low-friction, but DALC should capture cancellation reason and recent usage pattern before the user leaves.

DALC should not trap users. It should identify why the value was not strong enough.

## Re-Engagement Logic

| Situation | Re-engagement approach |
| --- | --- |
| Former member submits a new premium request | Reintroduce membership in context |
| User previously used multiple concierge requests | Offer return path tied to faster execution |
| Cancellation due to low usage | Re-engage only when relevant demand returns |

## Best Moments To Sell Membership Across DALC

1. after relocation completion when the user is now a resident with recurring needs
2. after founder setup when the user needs ongoing execution and support
3. after the second or third premium concierge request
4. during high-frequency nightlife, stay, transport, or custom execution usage

## Launch Recommendation

DALC should not launch membership on day 1 unless the operator layer can actually honor priority promises.

The correct recommendation is:

**Launch membership slightly after v1, once DALC proves repeat demand, stable response times, and reliable operator execution.**

Membership should be a retention multiplier, not an early revenue crutch.
